RETAIL SYSTEM · DEVICE DESIGN

Nafes: a retail system for a perfume shop, from the device to the cloud

Point of sale, stock and loyalty for a shop with a central depot and several shops. One Spring Boot backend serves three apps: a web admin, an Android app for sellers and a desktop app for the shop PC. Two Bluetooth LE devices, a wireless scanner and an oil scale, are in design.

PART 1 · THE SYSTEM · WORKS TODAY

01 / THE SHOP

How a perfume shop really sells

A central depot supplies several shops. A perfume is a fragrance sold by flacon size: the seller fills the flacon with fragrance oil and alcohol, so the system must know how much oil each size uses. Regular clients have a QR card and get rewards as they buy.

DEPOT → SHOPS

One depot, several shops

The depot receives the goods and sends them to the shops by transfer. Each location has its own stock and its own minimums.

50 ml → 10 ml oil

Flacon sizes

Each size stores its oil volume, so every sale takes the right amount of oil out of the stock. Flacon models are counted per size.

every 5th · every 10th

Clients and rewards

The system counts every item a client buys. By default, every 5th item is 20 % off and every 10th is free. Clients carry a printed QR card or open it on their phone.

⌁
One barcode per fragrance, not per flacon

A sticker on every flacon was too slow and too costly, and a theft risk when the seller turns away. So the seller scans the fragrance, then picks the size. Each fragrance gets an in-store EAN-13 code when it is created, and its label can be printed again from the stock page, one by one or in bulk.

02 / THREE APPS, ONE BACKEND

The office, the counter and the shop PC

The three apps share one REST API. The screenshots below come from the demo database, with generated names and figures.

A

Web admin · Angular

A dashboard for all shops or one shop, the catalogue, stock actions (receive at the depot, transfer to a shop, adjust, inventory by weight), clients, cards and reward rules, label printing and a web caisse.

B

Nafes Pro · Flutter, Android tablets

The caisse for sellers. The seller picks the fragrance from the list, scans its barcode with the camera or types it, then picks the size, the flacon model and the options. Open tickets are kept on the server, so a ticket can be put on hold and taken back later.

C

Shop PC · Spring Boot + Angular, offline first

One jar holds the backend and the Angular caisse, with its own MySQL on the PC. It runs as a Windows service and opens in a kiosk window. It keeps selling with no internet: each sale is written to an outbox in the same transaction, and a sync job sends it to the cloud when the line is back.

⌁
Low stock, and no double sale on a retry

An item below its location's minimum turns red, counts as an alert on the dashboard and can be added to a draft transfer in one click. A sale is never saved twice when the network retries: each shop PC sale has a UUID that the cloud records on arrival, so a resent sale is answered DUPLICATE, and each Nafes Pro checkout carries a request ID that is unique on the sale.

05 / WHY DEVICES

Two slow steps at the counter

Scanning with a tablet camera is slow at a busy counter: the seller has to aim the tablet at the label. And during an inventory, the seller weighs each oil bottle and types the weight by hand. Two small Bluetooth devices are planned to remove both steps.

01

Few app changes

The scanner will type like a keyboard, which the web caisse and the shop PC already accept.

02

Local radio

Bluetooth LE from the device to the tablet or PC next to it. No internet needed.

03

Cheap, local parts

An ESP32 board and common modules that can be bought in Tunisia.

04

Simple for sellers

One button, a beep and an LED. Nothing to set up at the counter.

01

Firmware pipeline

ESP-IDF in C, FreeRTOS tasks and the NimBLE stack.

RECEIVE → FRAME → FILTER → SEND → BEEP

The UART task will frame one code on CR/LF, or after 50 ms of silence. The filter will trim it, check it (printable, 1 to 256 characters) and drop the same code repeated within 1.5 s. The BLE task then sends it. The framing and filter logic will have no ESP-IDF dependency, so it can be unit-tested on a PC.

02

Mode A · BLE keyboard (default)

The scanner will type the code and Enter, like a USB scanner. The apps side already works today in the web caisse and on the shop PC: their scan detector takes 13 digits typed less than 50 ms apart, then Enter, with no field selected. So the firmware must send each key well within 50 ms. A keyboard sends key positions, not characters, so on an AZERTY PC the digit row arrives as &é"'(…, which the caisse already maps back to digits.

In Nafes Pro, typed codes work today only when the product search box is selected. Client QR cards go through the client search field in every app.

03

Mode B · Nafes Scan Service (planned fix)

A custom 128-bit service, so Nafes Pro will receive every scan without a selected field.

Scannotify · UTF-8 code, up to 244 bytes (MTU 247)
Statusread, notify · uint8: bit0 module OK, bit1 mode B
0x180ADevice Information
0x180FBattery

Holding the button at boot will switch the mode, saved in NVS.

07 / NAFES SCALE

An oil-bottle scale for the inventory

Inventory by weight works today. Each oil bottle in a shop has its own sticker and a stored empty weight. The seller scans the sticker, weighs the bottle and types the weight; the app turns it into millilitres of oil. The scale is the design part: the stable weight will arrive over Bluetooth instead of being typed.

ml = net ÷ density

The math (already in the app)

Net = weight − the bottle's empty weight. Millilitres = net ÷ the fragrance's density, 0.95 g/ml by default and set per fragrance.

01

Signal chain

LOAD CELL → HX711 → AVERAGE → STABLE? → BLE

A bit-banged driver will read channel A at gain 128, 10 samples per second, and keep SCK high for less than 60 µs, or the HX711 powers down. A moving average of 8 samples will smooth the reading. The weight is stable when 10 readings stay within ±1 g. An overload flag is set above 5 kg. Calibration will use a known mass, e.g. 500 g, and save the factor in NVS.

02

Nafes Scale Service

A custom 128-bit GATT service.

08 / SECURITY & RELIABILITY

Designed to stay out of the seller's way

A device that drops a scan or loses its settings costs a sale. The design plans for both.

LE Secure Connections

Pairing and bonding

Only bonded devices will be able to write commands to the scale.

1.5 s

Duplicate filter

The same code read twice within 1.5 s will be sent once.

Reconnect

Back on its own

The device will reconnect to the last bonded tablet or PC after a power cut.

NVS

Settings survive power cuts

The scanner mode, the bond and the scale's calibration factor will be kept in flash.

Watchdog

No blocking

Watchdog-friendly tasks, and no blocking work inside BLE callbacks.

Version 2

Signed updates

Planned: over-the-air updates with a signature check, and secure boot.
