FIRMWARE ARCHITECTURE

ESP-NOW Three-Channel Lamp Relay Node

Firmware for an ESP8266 relay board that switches three lamps on command from the IoT Network Gateway touchscreen. It pairs itself with the hub, only obeys that hub, and restores every lamp after a power cut.

02 / FIRMWARE ARCHITECTURE

A state machine driven from the main loop

App moves between a few explicit states. Each state does one thing and hands over to the next, so pairing, announcing and command handling never interleave.

APP STATES
stateDiagram-v2 [*] --> INIT INIT --> APP_CONNECT: hub MAC stored INIT --> APP_SCAN: no hub MAC yet APP_SCAN --> APP_CONNECT: hub found, MAC saved APP_CONNECT --> APP_ANNOUNCE APP_ANNOUNCE --> APP_IDLE APP_IDLE --> APP_HANDLE_COMMAND: command from hub APP_HANDLE_COMMAND --> APP_IDLE APP_IDLE --> APP_ANNOUNCE: every 60 s APP_IDLE --> APP_SCAN: FLASH held 5 s
01

Deferred command handling

The ESP-NOW receive callback runs inside the Wi-Fi stack, so it only checks the sender and copies the packet into a buffer. The main loop picks it up in APP_HANDLE_COMMAND, parses the JSON and drives the relays.

RECV_CB → COPY → PARSE → SWITCH → SAVE → PUBLISH

Only a real state change is written to EEPROM and published on the event bus, so a repeated command costs no flash write.

02

Event bus

A "lamp states changed" event carries a bit mask (bit n = lamp n+1). The OLED and the serial logger subscribe to it and don't know about the radio or the relays.

03

Persistent state

The hub MAC and the lamp states live in a small EEPROM layout, so the board comes back exactly as the hub's screen shows it.

0–5Hub MAC address
6Relay mask
7Magic byte 0xA5

03 / PROTOCOL

Small JSON over ESP-NOW

Messages follow the gateway's protocol: JSON text in one packet on channel 1. The switch never replies. The hub relies on the radio-level acknowledgement to know whether a command arrived.

{"type": "switch", "ch": 3}

Announce

Sent right after connecting, then every 60 s, well inside the hub's 5-minute offline window.

{"cmd": "set", "ch": 2, "on": true}

Command

Switches one lamp, or all three with ch: 0. Unknown channels and malformed JSON are ignored.

peer MAC

Only obeys its hub

Packets from any MAC other than the paired hub are dropped in the receive callback.

⚠
Mains voltage

The lamp side of the relays carries 230 V / 110 V. Use a properly rated, enclosed relay module and keep the low-voltage and mains wiring apart.

05 / PAIRING & RELIABILITY

Details that keep the lamps in sync

A

Self-pairing

With no hub stored, the board scans for an ESP-NOW… access point, connects, saves the hub's MAC and switches to ESP-NOW. It then appears in the hub's Devices list with a NEW badge.

B

Re-pairing

Holding FLASH for 5 s returns to the scan state. ESP-NOW is shut down and started again with the new hub's MAC.

C

No flicker at boot

Each relay pin's level is written before the pin becomes an output, so a lamp that was off stays off while the board starts.

D

Radio stays on channel 1

Wi-Fi auto-connect, auto-reconnect and modem sleep are disabled. A station that reconnects in the background would hop channels and miss the hub's commands.

06 / END-TO-END

From a tap to a lamp

One tap on the gateway's Lights screen travels through the radio, the state machine and the relay driver, and ends up saved and displayed on the node.

01 TAP Gateway Lights screen
02 SEND ESP-NOW + JSON
03 VERIFY Sender MAC

05 PERSIST EEPROM mask
06 NOTIFY OLED + serial
⌁
Engineering focus

The node reuses the weather sensor's architecture, so a third device type is mostly a new service plus a few states. Keeping radio callbacks minimal and doing the work in the main loop avoids races between the Wi-Fi stack and the relay, EEPROM and display code.
